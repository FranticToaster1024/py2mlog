# Contributing to py2mlog
Thank you for considering contributing to py2mlog! This file documents some information you may find useful.

However, it is important to first understand that this is but a toy project. I cannot guarantee active maintanence or updates, and I likely won't be dedicated enough to maintain this project long-term. If you find this project interesting enough to contribute to, it may be worth considering making your own fork to replace it instead.

# Issues
You can create a new issue [here](https://github.com/FranticToaster1024/py2mlog/issues/new). You can use these to raise bug reports, feature requests/suggestions, discuss code changes, request clarifications, or really anything related to this project.

# Code contributions
## Installing
To install in editable mode:

```sh
git clone --recurse-submodules https://github.com/FranticToaster1024/py2mlog.git
cd py2mlog
```

From here, there are 2 methods:
- with hatch
    ```sh
    hatch shell
    ```
    Tool commands:
    ```sh
    hatch check fmt
    hatch check code
    hatch run type-check
    hatch test
    ```

- without hatch
    ```sh
    python -m venv .venv
    .venv/Scripts/activate # or however you active a venv in your shell
    pip install -e ".[dev]"
    ```
    Tool commands:
    ```sh
    ruff format --check src/py2mlog/ tests/
    ruff check src/py2mlog/ tests/
    pyright .
    pytest tests/
    ```

## Code structure
### Mlog
Mlog instructions in `py2mlog` are not represented directly as text but rather typed `Instruction` dataclasses. All code related to this system can be found in the [`src/py2mlog/mlog/` folder](src/py2mlog/mlog/). This representation is generated by the compiler and converted to raw text in [`codegen.py`](src/py2mlog/mlog/codegen.py). Relevant tests can be found in the [`tests/mlog/` folder](tests/mlog/).

The `Instruction` dataclass (defined in [`instruction.py`](src/py2mlog/mlog/instruction.py)) is the core of this system. Its definition looks like this:
```py
@dataclass(frozen=True)
class Instruction:
    """
    Represent a single mlog instruction (including arguments).
    """

    type: InstructionType
    suboperation: Suboperation | None
    selectable_args: tuple[SelectableParam, ...]
    args: tuple[MlogArg, ...]
```

- `type` is an enum member of the `InstructionType` enum found in [`instruction_types.py`](src/py2mlog/mlog/instruction_types.py). For example, `InstructionType.READ`.

- `suboperation` is an enum member of any enum that subclasses the `Suboperation` class. The `Suboperation` class is a subclass of the `Enum` class. `Suboperation` and its subclasses can be found in [`suboperation.py`](src/py2mlog/mlog/suboperations.py). Examples include `DrawSuboperation.CLEAR` and `ControlSuboperation.SHOOT`.

    For the purposes of this project, suboperations are fields of an instruction that *change the shape or number of fields* (and have a limited list of possible values, but so far all fields that fulfil the first condition also fulfil the second.).

    For example:

    - the first field of the `control` instruction (e.g. `enabled`, `shoot` etc.) is a suboperation, because it changes the number of fields of the instruction. `control enabled block1 true` has 3 total fields (`enabled`, `block1`, `true`), while `control shoot turret1 x y true` has 5 total fields (`shoot`, `turret1`, `x`, `y`, `true`). Additionally, it also has a limited list of possible values, i.e. something like `control router foo bar baz` would be invalid.
    
- `selectable_args` a tuple of enum members of any enum that subclasses the `SelectableParam` class. The `SelectableParam` class is a subclass of the `Enum` class. `SelectableParam` and its subclasses can be found in [`selectable_params.py`](src/py2mlog/mlog/selectable_params.py). Examples include `RadarTargetSelectableParam.ENEMY` and `LookupSelectableParam.UNIT`. Note that a single instruction may carry multiple selectable parameters (e.g. `radar` carries 4), hence the tuple.

    For the purposes of this project, selectable parameters are fields of an instruction that ***do not** change the shape or number of fields* **and** have a limited list of possible values.

    For example:

    - the first field of the `lookup` instruction (e.g. `block`, `unit` etc.) is a selectable parameter. It has a limited list of possible values, i.e. something like `lookup duoBestTurret result id` would be invalid. It also does not change the number of fields of the instruction. `lookup block result id`, `lookup item result id` etc. all have 3 total fields.

- `args` is a tuple of `MlogArg`s (found in [`mlog_expressions.py`](src/py2mlog/mlog/mlog_expressions.py)). These **do not** have a limited list of possible values. These include variables, literal expressions, and jump destination labels.

### Compiler

Some utilities are used to make the compiler's job easier:

- [`error.py`](src/py2mlog/compiler/error.py) holds the code that handles the formatting of the error message and sometimes draws little arrows to tell you what went wrong:
    ```
    like this! >_<
         ^^^^
    ```

- [`emitter.py`](src/py2mlog/compiler/emitter.py) holds the emitter class which stores instructions and manages the generation of new temporary variables/labels.


The core compiler logic is in `compiler.py`. It traverses an abstract syntax tree (ast) constructed using the builtin `ast` module. 

Most nodes created by the builtin python `ast` module fall into two categories: `ast.expr` and `ast.stmt`. As such, the `Compiler` class mirrors this with its two main methods: `compile_expr` and `compile_stmt`.

`compile_expr` has a parameter called `output_expr`. It provides, well, the output expression that the compiled expression's result will be stored at. If it is `None`, a temporary variable is allocated instead. This allows the compiler to cleanly compile code such as
```py
x = a + b
```
to
```
op add x a b
```
instead of
```
op add some_tmp_var a b
set x some_tmp_var
```
